## Endpoint overview

The overview table in MIP-003 lists these endpoints:

| Endpoint | Method | Required | Purpose | Request | Response |
|---|---|---|---|---|---|
| `/start_job` | POST | yes | Start a job | `identifier_from_purchaser`, `input_data` | Job details with payment info |
| `/status` | GET | yes | Job status | query `job_id` | Status and optional input requirements |
| `/provide_input` | POST | no | Extra input for a job that is awaiting input | `job_id`, `input_schema_hash`, `input_data` | Success confirmation |
| `/availability` | GET | yes | Server operational check | none | Availability status |
| `/input_schema` | GET | yes | Expected input format | none | Input schema |
| `/demo` | GET | no | Demo data for marketing | none | Sample input and output |

So there are 4 required endpoints and 2 optional ones. The PRD (§9.1, §424) says there are "five MIP-003 endpoints". Per the source, the set is 6 endpoints: 4 required plus `/provide_input` and `/demo`, both optional.

No other endpoints are defined. `/health` is **not** part of MIP-003, although the CrewAI template serves it (see `crewai-quickstart.md`).

## POST /start_job

The request must follow the schema returned by `/input_schema`.

### Request body

| Field | Required | Type | Notes |
|---|---|---|---|
| `identifier_from_purchaser` | yes | string | Purchaser-chosen identifier. Example `"resume-job-123"`. |
| `input_data` | no (per table) | object | Keys are the `id`s defined in `/input_schema`. |

The request uses snake_case field names.

### Response body (200)

| Field | Required | Type | Example |
|---|---|---|---|
| `id` | yes | string | `18d66eed-6af5-4589-b53a-d2e78af657b6` |
| `blockchainIdentifier` | yes | string | `"block_789def"` (in practice the seller-signed identifier returned by Payment Service `POST /payment`) |
| `payByTime` | yes | int | Unix timestamp payment deadline, `1721480200` |
| `submitResultTime` | yes | int | Unix time the result must be submitted by |
| `unlockTime` | yes | int | Unix time the payment can be unlocked |
| `externalDisputeUnlockTime` | yes | int | Unix time until which disputes can happen |
| `agentIdentifier` | yes | string | Created at registration |
| `sellerVKey` | yes | string | "Wallet Public Key, accessible via the GET /payment_source/ endpoint in the Masumi Payment Service". The example value is an `addr1…` string. In the Payment Service this is the selling wallet's `walletVkey`, a payment key hash. |
| `identifierFromPurchaser` | yes | string | Echo of the request value |
| `input_hash` | yes | string | Hash of the submitted input (see MIP-004 below) |

The response uses camelCase names, except `id` and `input_hash`. This casing mix is copied exactly from the spec.

MIP-003 describes all four timestamps as "Unix timestamp" or "Unix Time Code" with integer examples of 10 digits (seconds). The spec does not say whether the unit is seconds or milliseconds. The Payment Service stores these values as datum `POSIXTime`, which is milliseconds; see `masumi-payment-service.md`.

### Errors

- `400`: `input_data` or `identifier_from_purchaser` is missing, invalid, or does not match the schema.
- `500`: job initiation failed.

## GET /status?job_id=…

### Query

| Parameter | Required | Type |
|---|---|---|
| `job_id` | yes | string |

### Response body

| Field | Required | Type | Notes |
|---|---|---|---|
| `status` | yes | string | Enum below |
| `input_schema` | no | object | Only needed when `status` is `"awaiting_input"`. It has the same shape as the `/input_schema` response: either `input_data: [...]` or `input_groups: [...]`. |
| `result` | no | string | Job result or pre-result, if available |

**Status enum values (exact strings):** `"awaiting_payment"`, `"awaiting_input"`, `"running"`, `"completed"`, `"failed"`.

The `/provide_input` prose says `"awaiting input"` with a space, but the enum value is `"awaiting_input"`.

### Errors

- `404`: `job_id` does not exist.
- `500`: status cannot be retrieved.

## POST /provide_input (optional)

### Request body

| Field | Required | Type | Notes |
|---|---|---|---|
| `job_id` | yes | string | |
| `input_schema_hash` | yes | string | SHA-256 of the **canonical JSON serialization** of the `input_schema` object from the `/status` response. Keys are sorted lexicographically with no unnecessary whitespace. The hash is lowercase hex, 64 chars. Example: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. |
| `input_data` | yes | object | Keys are the `id`s from the awaiting-input schema |

### Response body

| Field | Required | Type | Notes |
|---|---|---|---|
| `input_hash` | yes | string | Hash of the submitted input |
| `signature` | yes | string | "Cryptographic signature (Ed25519, similar to CIP-08) of the response data". It can be verified with the agent's Ed25519 verification key. Example is a 128-hex-char (64-byte) signature. The spec does **not** define the exact signed bytes. |

### Errors

`400` (invalid `job_id` or missing `input_data`), `404` (unknown `job_id`), `500`.

The response must contain **either** `input_data` **or** `input_groups`, never both.

| Field | Required | Type |
|---|---|---|
| `input_groups` | no | array of Group |
| `input_data` | no | array of Input Field |

**Group:**

| Field | Required | Type |
|---|---|---|
| `id` | yes | string (example is a UUID) |
| `title` | yes | string |
| `input_data` | yes | array of Input Field |

**Input Field** (MIP-003 table):

| Field | Required | Type | Notes |
|---|---|---|---|
| `id` | yes | string | Must be unique across the entire `input_schema` |
| `type` | yes | string | MIP-003 lists `"string"`, `"number"`, `"boolean"`, `"option"`, `"none"` |

| `data` | no | object | Type-specific config |
| `validations` | no | array of `{ "validation": string, "value": string }` | |

## Input validation schema (MIP-003 Attachment 01)

By default every field is required. Use the `optional` validation to relax that.

The attachment says input types "should be compatible with the HTML input types (except button types)".

**Full type list, as given in the attachment:**
`text | textarea | number | boolean | option | none | email | password | tel | url | date | datetime-local | time | month | week | color | range | file | hidden | search | checkbox | radio`.

`string`, which MIP-003 uses in its examples, is not in this list. The attachment uses `text` instead. Both appear in the ecosystem: the CrewAI template emits `"type": "string"`.

| Type | Common validations | Data fields |
|---|---|---|
| `none` | ignored | `description` (display-only) |
| `text` | `min`, `max`, `format: nonempty` | `placeholder`, `description`, `default` |
| `textarea` | `min`, `max`, `format: nonempty` | `placeholder`, `description`, `default` |
| `number` | `min`, `max`, `format: integer` | `placeholder`, `description`, `default` |
| `boolean` | `optional` | `description`, `default` |
| `email` | `format: email` (auto), `min`, `max` | `placeholder`, `description`, `default` |
| `password` | `min`, `max` | `placeholder`, `description` |
| `tel` | `format: tel-pattern`, `min`, `max` | `placeholder`, `description`, `default` |
| `url` | `format: url` (auto), `min`, `max` | `placeholder`, `description`, `default` |
| `date`, `datetime-local`, `time`, `month`, `week` | `min`, `max` | `description`, `default` |
| `color` | none | `default`, `description` |
| `range` | `min`, `max` | `min`, `max`, `step`, `default`, `description` |
| `file` | `accept`, `min`, `max` | `description`, `outputFormat` (required; only `"url"` is supported) |
| `hidden` | none | `value` (required) |
| `search` | `min`, `max`, `format: nonempty` | `placeholder`, `description`, `default` |
| `checkbox` | `optional` | `description`, `default` |
| `radio` | `optional` | `values` (required), `default`, `description` |
| `option` | `min`, `max` (count of selected options) | `values` (required array of strings), `description` |

**Validation rules** (`validation` → meaning):

- `min`: minimum length for text, password, tel, and search; minimum value for number and range; minimum date or time; minimum number of selected options for `option`. Inclusive. If set, it must be `>= 1`. For fields that are not required, use `optional` instead.
- `max`: the same semantics as `min`, as an upper bound. Inclusive.
- `format`: one of `email`, `url`, `nonempty`, `tel-pattern`, `integer` (number only).
- `accept`: an HTML `accept` string for `file`, e.g. `"image/*,.pdf,.doc,.docx"`.
- `optional`: the field is not required. The default is false. The example shows `value` as `"true"`/boolean.
- All `value`s are **strings**, e.g. `{"validation":"min","value":"1"}`.
- Repeated validations combine as a logical AND.
- The spec warns: "Ensure that the value you receive in your agent is validated to your needs and handled as untrusted data. This schema is a suggestion to frontend on how to display inputs."

## How `input_hash` is computed (MIP-004)

MIP-003 says only "Hash of the input data submitted". The algorithm is defined in MIP-004 (Draft):

1. `canonical = JCS(input_data)`, using the JSON Canonicalization Scheme, RFC 8785, interpreted as UTF-8.
2. `preimage = identifier_from_purchaser + ";" + canonical`.
3. `input_hash = lowercase_hex(SHA-256(UTF-8(preimage)))`, 64 hex chars.

Output (result) hash, which is used for `submitResultHash` / datum `result_hash`:

1. `preimage = identifier_from_purchaser + ";" + output`, where `output` is the raw UTF-8 string.
2. `result_hash = lowercase_hex(SHA-256(UTF-8(preimage)))`.

The reference Python implementation in MIP-004 uses `canonicaljson.encode_canonical_json(input_data)` from the `canonicaljson` package for step 1.

**Observed implementation drift:** `pip-masumi` 1.2.0 (`masumi/helper_functions.py`, commit `5a54f5e0755a1b7de52ae1823d767fe442b1ac13`) computes the input hash exactly as above. Its `create_masumi_output_hash` does **not** hash the raw output. It first applies `json.dumps(output_string, ensure_ascii=False)[1:-1]`, which JSON-escapes the string, and hashes `identifier_from_purchaser + ";" + escaped`. For outputs that contain quotes, backslashes, or newlines, this differs from MIP-004 step 2.1 ("raw UTF-8 string"). A Cascade verifier that must match hashes produced by Masumi agents on chain has to reproduce the pip-masumi variant.

The examples in MIP-003 show a 32-hex-char `input_hash` (`a87ff679…`). That value is illustrative only and does not match MIP-004 (64 hex).
